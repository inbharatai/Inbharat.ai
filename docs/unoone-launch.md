## Publishing a download

No final signed UnoOne installers were supplied for publication in this change set. Consequently platform artifact records start as `null`; the site provides a real contact/access path rather than inventing a download.

After the owner approves the actual release:
1. Identify the immutable source/build and the specific shipping distribution. Development features are not automatically enabled in release variants.
2. Verify appropriate signing, exact version, file size and SHA-256, supported hardware/platforms, installation and safe upgrade/data preservation.
3. Complete current-build acceptance of the advertised workflows, permissions, network boundaries and failure/recovery behavior. Do not add historical full-suite counts to later subsets.
4. Publish the approved artifact and stable requirements/setup/release-notes/license/support URLs through an approved host.
5. Populate the typed artifact record with the verified metadata. `approvedArtifact` checks configuration completeness; it does **not** cryptographically verify a signature, download the artifact, or certify the runtime.
6. Rebuild, inspect the rendered availability/download link, and verify the actual hosted asset, headers and checksum. Test direct route loads and client navigation.

Never publish supplied development APKs, source ZIPs, internal technical publications or the investor film merely because they were uploaded for review. Do not add a store badge without a real listing, fabricate prices/ratings, or use an expiry-bound URL as a durable release destination.
